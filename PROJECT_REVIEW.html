Blog Microservices — Principal Engineering Review

Repository 29goku/-blog-microservices · Spring Boot 3 / Spring Cloud · React + Vite · Kafka · Redis · Postgres · Kubernetes/Helm

Scope: what the system does, how it is built, and an evidence-based registry of what is wrong, risky, or improvable — with fixes and a roadmap. Findings cite files and lines; items marked verify were not fully inspected.

1. Executive summary

Verdict: A well-organised learning/demo platform with admirable breadth (7 services, event streaming, caching, tracing, 5 deployment targets). It is not production-safe: authorization is effectively absent below the gateway, secrets are placeholders committed to git, inter-service calls are fragile and N+1, there are zero automated tests, and the Kubernetes manifests lack the basics for resilience. Most of the critical items are cheap to fix and should be done before any real user data is stored.

    2. What the project does

    A multi-user blogging platform. Users register and log in, publish posts with tags, comment, and like/dislike posts. The system also ships a developer-facing "request tracking" demo in the gateway that visualises which service handled each request.

    👤 Accounts

    Register, login (JWT, 1h), profile CRUD.

    📝 Posts

    CRUD, title search, tags, cached list/detail, comment count.

    💬 Comments

    Comment on posts; publishes comment-created to Kafka.

    👍 Reactions

    Like/dislike toggle, counts per post.

    🏷 Tags

    Tag CRUD and post↔tag association.

    🔍 Request tracker

    Gateway keeps the last 100 requests in memory for a UI visualiser.

    4. Service deep dive

    api-gateway

    • JwtAuthFilter: validates HS256, injects X-User-Id/X-Username.
    • Public: /api/auth/*, /actuator*, POST /api/users, all GET on posts/tags/comments/likedislike.
    • No downstream service reads those headers.
    • CORS defined twice (Java + YAML), conflicting.
    • RequestTracking: HashMap + LinkedList not thread-safe; per-instance.

    • SecurityFilterConfig: csrf.disable() + anyRequest().permitAll().

    post-service

    • CRUD + search; Redis cache; Kafka consumer for comment count.

    • N+1: per post user + tag HTTP calls.

    comment-service

    5. Key request flows

    Login

    1. SPA POST /api/auth/login (public).
    2. user-service BCrypt-verifies, signs HS256 JWT (1h).
    3. SPA stores token + userId in localStorage.
    4. Later calls send Authorization: Bearer; gateway verifies and adds headers that nobody consumes.

    Create post

    1. Body contains userId (client-chosen).
    2. post-service calls user-service to check it exists; any error ⇒ “User not found”.
    3. Save to DB, evict cache, kafkaTemplate.send — three non-atomic steps.

    Comment → count

    1. comment-service saves, publishes comment-created.
    2. post-service listener: read, +1, save (lost updates under concurrency; replay double-counts), System.out.println.
    3. Cache invalidation via Redis pub/sub.

    Like toggle

    1. Body has userId+postId.
    2. HTTP to post-service (full post + user + tags) and user-service.
    3. findByUserIdAndPostId then save/delete — no unique key ⇒ duplicates.

    Gateway deep dive: api-gateway

    The gateway is the only component that authenticates. Everything downstream is permitAll. Its correctness therefore defines the security of the whole platform, and it is the single most important module to harden.

    Request pipeline

    1. Request arrives on Spring Cloud Gateway (WebFlux, Netty).
    2. RequestTrackingFilter (demo logic: hard-coded ports 8081-8084) records hops for the frontend sidebar.
    3. JwtAuthFilter (order HIGHEST_PRECEDENCE+1) decides public vs protected, validates the HS256 token, and injects X-User-Id and X-Username.
    4. Route predicate matches /api/<svc>/** and resolves lb://<svc> via Eureka (or a *_URL override).
    5. No timeout, retry, rate limiter or circuit breaker filter is configured on any route.

    The public-path allow-list

    // JwtAuthFilter.java:56-66 (paraphrased)

  if (path.startsWith("/api/auth/")) return true;
  if (path.startsWith("/actuator"))  return true;      // gateway routes + prometheus exposed

  if (m == GET && (path.startsWith("/api/posts") || path.startsWith("/api/tags")
      || path.startsWith("/api/comments") || path.startsWith("/api/likedislike"))) return true;
  return false;
}

    Two conflicting CORS configurations

    # application.yml:36-42
globalcors:
  corsConfigurations:
    '[/**]':
      allowedOriginPatterns: "*"
      allowCredentials: true

    GatewayConfig.corsWebFilter separately allows localhost:* and *.vercel.app with credentials. Two sources of truth means the effective policy depends on filter ordering. *.vercel.app permits any tenant on Vercel (including an attacker's) to make credentialed calls. Because the token lives in localStorage and is sent as a header, the practical blast radius is smaller than with cookies, but the policy is still wrong and would become critical the moment cookies are adopted. Fix: one config, explicit origin list from env, allowCredentials only if cookies are used.

    Resilience and traffic management gaps

    • No TimeLimiter/response-timeout or connect-timeout in spring.cloud.gateway.httpclient. A hung downstream ties up connections indefinitely.
    • No RequestRateLimiter (Redis is already deployed, so a token-bucket limiter is cheap). Login and signup are brute-forceable.
    • No retry for idempotent GETs and no CircuitBreaker filter with fallback.
    • No request-size limit; no security headers (HSTS, X-Content-Type-Options, CSP).
    • com.blog and gateway logging at DEBUG, trace sampling probability 1.0: expensive and may log tokens or bodies.

    Deep dive: user-service

    Owns identity: signup, login, JWT issuance, profile CRUD. Uses BCrypt (good) and a constructor-injected UserService (good). Everything else below is a gap.

    SecurityFilterConfig: no authentication of its own

    http.csrf(c -> c.disable())
    .authorizeHttpRequests(a -> a.anyRequest().permitAll());

    This is acceptable only if the service is unreachable except through the gateway. The repo contradicts that assumption: docker-compose publishes service ports, the Render and Railway configs expose services publicly, and a Kubernetes NodePort or missing NetworkPolicy allows any pod to call it. Anyone with network reach can DELETE /api/users/{id} with no token. Fix: make each service an OAuth2 resource server that validates the JWT itself (defence in depth), and add NetworkPolicy default-deny.

    JwtService

    Jwts.builder().setSubject(username).claim("userId", id)
    .setIssuedAt(now).setExpiration(now + expirationsMs)   // typo in field name
    .signWith(Keys.hmacShaKeyFor(secret.getBytes()), HS256)
    • Symmetric secret shared between user-service and gateway; either leak lets an attacker mint admin tokens. A placeholder default (dev-only-secret-change-me-please-32chars+) is present in six places, so a deployment that forgets to override is silently forgeable.
    • No iss, aud, jti; no refresh token; no revocation or logout. A stolen token is valid until expiry.
    • No roles/scopes claim, so authorisation beyond "logged in" is impossible (no admin concept for tag management, moderation, etc.).
    • Secrets shorter than 32 bytes throw WeakKeyException at runtime rather than failing configuration validation on boot.

    Cross-service coupling

    PostEventListener consumes post events to maintain postCount. Same lost-update and non-idempotency pattern as the post-service comment counter (see Kafka section).

    Deep dive: post-service

    The largest and most complex service (CRUD, search, Redis cache, Kafka producer and consumer, Feign to user and tag services). It carries most of the correctness and performance debt.

    createPost: five side effects, zero atomicity

    // PostService.createPost (lines 45-75, condensed)
try { userClient.getUserById(postDTO.getUserId()); }          // sync remote call
catch (Exception e) { throw new RuntimeException("User not found"); }  // masks timeouts
Post saved = postRepository.save(post);                       // 1. DB write
cachePublisher.publishAllInvalidated();                       // 2. Redis pub/sub
kafkaTemplate.send("post-created", event);                    // 3. Kafka, fire and forget
    • Identity from the body: postDTO.getUserId() is trusted instead of the gateway-injected X-User-Id. Any logged-in user posts as anyone.
    • Dual write: if Kafka is down after the DB commit, user-service's postCount never updates; if the process dies between steps 1 and 3 the event is lost forever. Use the transactional outbox pattern (event row in the same transaction, relay via Debezium or a poller).
    • Error masking: the blanket catch converts a 5s Feign timeout, a 500, and a real 404 all into "User not found" (client sees 4xx or 500 inconsistently).
    • The remote user check is redundant once the gateway has authenticated the caller: the token already proves the user existed at issue time.

    CommentEventListener: lost updates and double counting

    @KafkaListener(topics="comment-created", groupId="post-service-group")
public void on(CommentCreatedEvent e){
  System.out.println("received " + e);
  Post p = postRepository.findById(e.getPostId()).get();   // read
  p.setCommentCount(p.getCommentCount()+1);                // modify
  postRepository.save(p);                                  // write
}
    • Two concurrent events for one post both read N and both write N+1: lost update. Redelivery after a rebalance double-counts: not idempotent.
    • .get() throws on a deleted post, so the listener fails and Kafka retries the poison message forever (no DLT).
    • System.out.println bypasses logging, MDC and trace correlation.

    Fix (atomic): @Modifying @Query("update Post p set p.commentCount = p.commentCount + 1 where p.id = :id"), store processed eventId in a table with a unique constraint, and configure DefaultErrorHandler with DeadLetterPublishingRecoverer and bounded back-off. Better still: derive the count with SELECT count(*) cached, or accept eventual consistency explicitly.

    RedisCacheConfig

    ObjectMapper om = new ObjectMapper();                       // bare mapper
om.activateDefaultTyping(LaissezFaireSubTypeValidator..., NON_FINAL);
RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofSeconds(60))
    .disableCachingNullValues();
    • Security: default typing with a permissive validator is the classic Jackson polymorphic deserialization gadget surface. Anyone able to write to Redis (unauthenticated Redis on the cluster network, see infra) gains code execution potential. Use BasicPolymorphicTypeValidator allow-listing com.blog.*, or GenericJackson2JsonRedisSerializer with a typed mapper per cache.
    • Single TTL for every cache; no jitter, so synchronized expiry leads to stampedes on allPosts. Add per-cache TTLs with random jitter and @Cacheable(sync=true).
    • Pub/sub invalidation (post-cache-invalidate) is at-most-once: a replica that is restarting misses the message and serves stale data until TTL. Fine given the 60s TTL, but the complexity buys little over plain TTL plus targeted evicts.

    application.yml

    • ddl-auto: update in production images: schema drift, no rollback, no review. Adopt Flyway/Liquibase and set validate.
    • Feign logger-level: full logs request and response bodies (may include PII, tokens).
    • Resilience4j instances for post-service, user-service, tag-service are declared with identical settings, but no @CircuitBreaker or Feign fallback was found wired to them (verify); configuration without use gives false assurance.
    • Datasource defaults postgres/postgres against the shared main_db (see data section).

    Deep dive: comment, like-dislike and tag services

    comment-service

    // createComment
userClient.getUserById(dto.getUserId());      // sync call 1

    • Existence validation fetches full DTOs. getPostById itself calls user-service, so one comment creation fans out into 3+ synchronous hops on the request path. Replace with HEAD/exists endpoints or a local read-model of post ids fed from Kafka.
    • Blanket catch rethrows InvalidCommentException, so an outage reads as "invalid comment" (400) instead of 503.
    • Fire-and-forget Kafka send with no callback, no outbox: if the broker is down the comment persists but the count never increments.

    IDOR walk-through

    # Attacker is user 7, victim is user 3. One valid token for user 7 is enough.
curl -X PUT  $GW/api/users/3  -H "Authorization: Bearer $T7" -d '{"email":"x@evil.tld"}'
curl -X DELETE $GW/api/posts/42 -H "Authorization: Bearer $T7"
curl -X POST $GW/api/posts -H "Authorization: Bearer $T7" -d '{"userId":3,"title":"as victim"}'

    All three succeed. This is the highest-impact finding in the review and can be closed in a day: compare X-User-Id with the resource owner in each service, and delete userId from write DTOs.

    Secrets

    • Helm secrets.yaml templates Kubernetes Secret.stringData from values.yaml; secrets live in git in clear text. Use External Secrets/SealedSecrets/SOPS plus a cloud secret manager.
    • Default DB credentials postgres/postgres and the placeholder JWT secret are baked into config defaults. Fail fast on boot if the secret equals the placeholder.
    • .gitignore does not exclude .env, .claude/, or credential files. Add them and run gitleaks in CI plus a history scan.

    Frontend token handling

    client.ts keeps the JWT in localStorage('authToken') (readable by any XSS), also stores authUserId and sends it in bodies (feeding IDOR). A 401 clears storage, but there is no expiry decode, silent refresh or logout call. Prefer short-lived access tokens in memory plus an httpOnly, SameSite refresh cookie, and add a CSP.

    Data model and consistency

    • Shared database: all five data services use one main_db with default postgres superuser. This couples schemas, defeats service autonomy, and one runaway query affects all. Move to schema-per-service with distinct roles (cheap), then database-per-service if scale demands.
    • Schema management: ddl-auto: update in all five services. No migrations, no rollback, silent drift, risky column renames. Introduce Flyway with a baseline migration, set validate.
    • Constraints: unique on username, email, tag name, (user, post) vote and (post, tag) are unconfirmed or absent; no foreign keys can exist across services, so referential integrity is enforced only by chatty sync validation, which is itself racy.
    • Indexes: none declared on post.user_id, comment.post_id, like_dislike(post_id), post_tag(post_id); title search unindexed.
    • Types: epoch Long timestamps in some entities, mixed styles in others. Standardise on Instant / timestamptz.
    • Derived counters (commentCount, postCount) maintained by consumers: lost updates and non-idempotency (see post-service).
    • Deletion semantics: deleting a user or post leaves orphans in other services. Emit UserDeleted/PostDeleted events with idempotent cleanup consumers, or soft-delete.
    • Pagination: every list endpoint is unbounded.

    Kafka and event design

    TopicProducerConsumerIssue
    post-createdpost-serviceuser-service (PostEventListener)Dual write; counter not idempotent.
    comment-createdcomment-servicepost-service (CommentEventListener)Dual write; lost update; no DLT; println.
    • Delivery guarantees: producers use default settings: no acks=all, no enable.idempotence, no send callback. Failures vanish silently.
    • Schema: events are Java classes duplicated per service and serialised with JSON; no schema registry, no versioning, no eventId / occurredAt envelope. A field rename breaks consumers at runtime.
    • Error handling: no DefaultErrorHandler, back-off, retry topic or dead-letter topic; one poison message stalls the partition.
    • Topology: single Zookeeper + single Kafka broker (cp-kafka 7.4.0), replication factor 1, topics auto-created. Any restart loses availability; disk loss loses data. Migrate to KRaft and 3 brokers for production, or a managed service.
    • Is Kafka justified? For two counter updates, a broker plus Zookeeper is heavy. Either commit to events (outbox, more consumers: search index, notifications, analytics) or compute counts via query and cache.

    Redis and caching strategy

    • Redis 7.0.11 single instance, no password, no persistence policy, no maxmemory-policy. Treat as a cache: set maxmemory + allkeys-lru, require auth/TLS, restrict via NetworkPolicy.
    • One global 60s TTL with no jitter; allPosts is a single hot key that expires for all readers simultaneously (stampede). Use sync=true, jitter and stale-while-revalidate.
    • Cached DTOs embed cross-service data (user name, comment count), so cache correctness depends on three services. Cache only data the service owns.
    • Pub/sub invalidation post-cache-invalidate is lossy; publishAllInvalidated wipes everything on every create, which erodes hit ratio under write load.
    • Redis is the obvious backing store for the missing gateway rate limiter and, optionally, a token deny-list.
    • Jackson default typing: see Security (deserialisation risk).

    API contract review

    • Errors: inconsistent. Blanket catches produce generic 500 or 400 for everything; no problem+json; messages leak internals.
    • Verbs/semantics: toggle-by-POST returns null; DELETE on a missing row yields 500; PUT performs partial update (should be PATCH).
    • Identity in payloads: userId in request bodies. Derive from token.
    • Pagination/sorting/filtering: absent. Standardise on ?page&size&sort or cursor.
    • Versioning: no /v1 prefix; DTO duplicates across services drift.
    • Documentation: a Postman collection and prose docs exist but no OpenAPI. Add springdoc-openapi per service, aggregate at the gateway, and generate the TypeScript client from it.
    • Entity leakage: tag-service returns JPA entities directly.
    • Validation: add @Valid, @NotBlank, @Email, size limits, and a global @RestControllerAdvice.

    Frontend review (React + Vite + TypeScript)

    Components: CommentSection, ConfirmDialog, CreateUserForm, Dialog, LikeDislikeButton, LoginScreen, PostForm, PostList, RequestFlowSidebar, TagManager, plus api/, services/, App.tsx, main.tsx.

    • Token storage: localStorage; no expiry awareness; 401 handler clears storage but does not redirect or refresh cleanly.
    • Client trusts itself: stores authUserId and sends it in bodies; UI hides buttons for non-owners but the server does not enforce, so the UI gives false assurance.
    • Data fetching: hand-rolled calls; adopt TanStack Query for caching, retries, invalidation and loading/error states; fixes duplicate fetches after mutations.
    • Lists: loads all posts at once; add pagination or infinite scroll and virtualisation.
    • Demo code in product: RequestFlowSidebar relies on gateway tracking headers hard-coded to ports 8081-8084; useful for teaching, but should be behind a feature flag and not part of the prod path.
    • Accessibility: verify dialog focus trapping, labelled inputs, keyboard operation of like buttons, colour contrast (Dialog, ConfirmDialog).
    • Tests/lint: no component tests; add Vitest + Testing Library, ESLint, tsc --noEmit in CI.
    • Delivery: VITE_API_URL is build-time; one build per environment. Prefer same-origin /api behind the ingress/CDN, which also removes the need for CORS.

    Docker, Kubernetes, Helm, Compose

    Docker

    • Root user, no HEALTHCHECK, no JVM memory flags, tag-pinned base images, -DskipTests, || true masking errors. Other services' Dockerfiles likely identical (verify): extract a shared pattern or use Jib/Buildpacks with a distroless JRE, non-root user, layered jars.

    Kubernetes (k8s/, kind-oriented)

    • No livenessProbe, no resources requests/limits, no HPA, no PDB, no securityContext, no NetworkPolicy.
    • Postgres, Kafka, Zookeeper, Redis as single-replica Deployments/StatefulSets without backups; stateful infra should be managed services or operators.
    • Eureka runs next to native k8s DNS: two discovery systems.

    Helm (helm/blog/)

    • Duplicates k8s/ manifests: two sources of truth that will diverge. Keep Helm only and generate kind config from values.
    • imagePullPolicy: Never in templates (kind-only). Breaks any real cluster; make it a value.
    • replicas: 1 hard-coded; secrets in values.yaml; no probes/resources in the sampled template.
    • Every template repeats near-identical Deployment+Service blocks: use a shared named template or a library chart.

    Compose, Render, Railway

    • Configuration is replicated across five deployment flavours (compose, Render, Railway, k8s, Helm), and the same env names are re-declared each time. Pick one primary target and generate the others, or delete the unused ones.
    • Published host ports defeat the "only gateway is reachable" assumption (verify compose port mappings).
    • grafana/ provisioning file is named dashbaords.yml (typo): Grafana provisioning may not pick it up depending on how it is referenced.

    Observability

    • Present: Micrometer + OTLP tracing to otel-collector, Prometheus endpoints, Grafana provisioning. Good foundation.
    • Problems: sampling probability 1.0 everywhere (cost and overhead; use 0.05-0.1 or tail-based sampling at the collector); OTLP endpoint hard-coded to http://otel-collector:4318 so it cannot be overridden without a rebuild; DEBUG logging for com.blog; System.out.println in the listener; Feign full logging.
    • Missing: structured JSON logs with traceId, business metrics (posts created, cache hit ratio, consumer lag), SLOs and alerts, dashboards-as-code reviewed, Kafka lag exporter, health groups (liveness vs readiness).
    • Actuator is publicly routable through the gateway (security issue as well).

    Migration strategy: how to change a live system safely

    1. Strangler – put new behaviour behind gateway routes; migrate one route at a time.
    2. Expand / contract schema – add nullable column, dual-write, backfill, switch reads, drop old column in a later release.
    3. Outbox first – before any event redesign, make publishing reliable.
    4. Parallel run – compare old and new responses (shadow traffic) for the batch-endpoint rewrite.
    5. Feature flags – decouple deploy from release; kill switches for risky paths.
    6. Rollback rule – every change documents its rollback; data migrations are forward-compatible for one release.
    -- expand/contract example
ALTER TABLE likes ADD COLUMN user_post_key text;
UPDATE likes SET user_post_key = user_id||':'||post_id;   -- backfill in batches
CREATE UNIQUE INDEX CONCURRENTLY ux_likes_user_post ON likes(user_post_key);

    8. Target architecture & ADRs

    1. ADR-1 AuthN/Z: gateway verifies JWT; every service is a resource server (validates JWT itself or trusts mTLS + signed internal header) and derives user from the token, never the body. Ownership checks in service layer; roles (USER/ADMIN).
    2. ADR-2 Secrets: external secret store (Sealed Secrets / External Secrets / Vault); RS256/EdDSA keys with kid, rotation, iss/aud, refresh tokens or short access TTL.
    3. ADR-3 Resilience: Resilience4j timeout + retry (idempotent only) + circuit breaker + bulkhead on every client; gateway rate limiting (Redis).
    4. ADR-4 Data: Flyway migrations, ddl-auto: validate, schema/DB per service, FK-free cross-service IDs, indexes on postId/userId.
    5. ADR-5 Events: outbox pattern, versioned event schemas (Avro/JSON schema), idempotent consumers, DLQ.
    6. ADR-6 Platform: one source of truth (Helm or Kustomize), HPA, PDB, NetworkPolicy, resources, probes, non-root, StatefulSets with PVCs or managed Postgres/Kafka/Redis.
    7. ADR-7 Quality gates: CI with build, unit+integration (Testcontainers), contract tests, SpotBugs/Checkstyle, dependency + image scanning, secret scanning.
