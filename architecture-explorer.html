The big picture

Your blog, built as many small apps working together

Instead of one giant program, this project is split into several small, independent services. Each one owns a single job and its own database. They talk to each other over the network, and a single front door (the API Gateway) sits in front of them all. Here's the whole thing, top to bottom.

🏢 Analogy: Think of a big office building. The reception desk (API Gateway) greets every visitor and directs them to the right department (a service). Each department has its own filing cabinet (database) and never rummages through another department's files — it just calls them on the phone (an API call).

Why build it this way?

🧩

Independent

Each service can be built, deployed, and scaled on its own. A bug in comments won't take down posts.

🎯

Focused

Every service has one clear responsibility, so the code stays small and easy to reason about.

📈

Scalable

Busy services (like posts) can run more copies without touching the rest of the system.

Fire-and-forget, not ask-and-wait

Events: the other way services talk

Feign calls are synchronous — "ask a question, wait for the answer." Kafka events are asynchronous — "announce something happened, and whoever cares can react whenever they're ready." No response is expected, and the publisher doesn't even know who's listening.

📌 Analogy: A Feign call is a phone call — you dial, you wait, you get an answer. A Kafka event is a notice pinned to a board — you pin it and walk away; anyone interested reads it later, on their own schedule.

The two event flows today

Why counts are updated this way

Before Kafka, keeping User.postCount or Post.commentCount accurate would have meant one more synchronous Feign call on every write — one more thing that could fail or add latency. Instead, the writing service saves its own row, fires an event, and moves on. The counter update happens moments later, in the background, in a different service. If the listener is briefly down, the message waits in Kafka until it's back — nothing is lost, and the original request was never blocked on it.

⚠️ Cloud caveat: Kafka + Zookeeper are wired up in docker-compose.yml for local/Docker use, but render.yaml doesn't provision them yet. That means on the live Render deployment these two listeners currently have nothing to consume — counts won't sync there until a managed Kafka is added to the cloud config.

The pattern that repeats everywhere

Inside one service: the layers

Here's the part that feels complicated at first — but it's the same shape in every service. Once you understand one, you understand them all. A request falls through these layers like water down steps.

🍔 Analogy: A restaurant. The Controller is the waiter (takes your order, brings the food). The Service is the chef (does the actual cooking / business rules). The Repository is the pantry clerk (fetches & stores ingredients). The Database is the pantry itself. The DTO is the plate the food is served on — a clean shape for handing data around.

How everything wires together

Interconnectivity & dependencies

Three kinds of "depends on" exist here. Understanding which is which clears up most of the confusion.

1 · Runtime service graph (who calls whom)

Solid blue arrows = live HTTP calls via @FeignClient at runtime. Dashed pink arrows = async Kafka events — the publisher doesn't wait for a response. Together these are the full map of inter-service communication.

Feign HTTP call (validation / enrichment)    Kafka event (async, fire-and-forget)

2 · Build-time dependencies (Maven)

🏗️

Parent POM aggregates modules

The root pom.xml is <packaging>pom</packaging> and lists all 7 modules. It centralises the Spring Boot 3.3.0 parent, Java 17, and Spring Cloud 2023.0.3 via dependencyManagement, so every service uses matching versions.

🔗

A real module→module dependency

post-service declares a compile dependency on the tag-service module (to reuse its tag DTO/types). This is the one place a service depends on another's code at build time — everything else is loose HTTP coupling.

3 · Configuration dependencies (env vars)

Nothing is hard-coded. Services find their database and each other through environment variables, with sensible local defaults. Same code runs locally, in Docker, and on Render.

🧠 The golden rule: services are loosely coupled at runtime (HTTP + circuit breakers) but version-aligned at build time (one parent POM). Change one service's internals freely — as long as its HTTP contract stays the same, nobody else breaks.

The cool bit: live request tracking

📊

RequestFlowSidebar

Polls /api/tracking/requests every ~1.5s and shows the last requests that hit the gateway in real time — method, path, target service, duration, status. Great for seeing the architecture work.

🗺️

fileMapping.ts

Maps each request to the backend files involved, so the dashboard can teach you which Controller/Service/Repository handled it. A learning tool baked right into the UI.

🧠 Key idea: The frontend stays "dumb" about the backend's shape. It knows one address (/api) and lets the gateway hide all the complexity of which service lives where.
