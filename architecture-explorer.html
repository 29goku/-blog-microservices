The big picture

Your blog, built as many small apps working together

Instead of one giant program, this project is split into several small, independent services. Each one owns a single job and its own database. They talk to each other over the network, and a single front door (the API Gateway) sits in front of them all. Here's the whole thing, top to bottom.

🏢 Analogy: Think of a big office building. The reception desk (API Gateway) greets every visitor and directs them to the right department (a service). Each department has its own filing cabinet (database) and never rummages through another department's files — it just calls them on the phone (an API call).

Why build it this way?

🧩

Independent

Each service can be built, deployed, and scaled on its own. A bug in comments won't take down posts.

🎯

Focused

Every service has one clear responsibility, so the code stays small and easy to reason about.

📈

Scalable

Busy services (like posts) can run more copies without touching the rest of the system.

Fire-and-forget, not ask-and-wait

Events: the other way services talk

Feign calls are synchronous — "ask a question, wait for the answer." Kafka events are asynchronous — "announce something happened, and whoever cares can react whenever they're ready." No response is expected, and the publisher doesn't even know who's listening.

📌 Analogy: A Feign call is a phone call — you dial, you wait, you get an answer. A Kafka event is a notice pinned to a board — you pin it and walk away; anyone interested reads it later, on their own schedule.

The two event flows today

Why counts are updated this way

Before Kafka, keeping User.postCount or Post.commentCount accurate would have meant one more synchronous Feign call on every write — one more thing that could fail or add latency. Instead, the writing service saves its own row, fires an event, and moves on. The counter update happens moments later, in the background, in a different service. If the listener is briefly down, the message waits in Kafka until it's back — nothing is lost, and the original request was never blocked on it.

⚠️ Cloud caveat: Kafka + Zookeeper are wired up in docker-compose.yml for local/Docker use, but render.yaml doesn't provision them yet. That means on the live Render deployment these two listeners currently have nothing to consume — counts won't sync there until a managed Kafka is added to the cloud config.

How everything wires together

Interconnectivity & dependencies

Three kinds of "depends on" exist here. Understanding which is which clears up most of the confusion.

1 · Runtime service graph (who calls whom)

Solid blue arrows = live HTTP calls via @FeignClient at runtime. Dashed pink arrows = async Kafka events — the publisher doesn't wait for a response. Together these are the full map of inter-service communication.

Feign HTTP call (validation / enrichment)    Kafka event (async, fire-and-forget)

2 · Build-time dependencies (Maven)

🏗️

Parent POM aggregates modules

The root pom.xml is <packaging>pom</packaging> and lists all 7 modules. It centralises the Spring Boot 3.3.0 parent, Java 17, and Spring Cloud 2023.0.3 via dependencyManagement, so every service uses matching versions.

🔗

A real module→module dependency

post-service declares a compile dependency on the tag-service module (to reuse its tag DTO/types). This is the one place a service depends on another's code at build time — everything else is loose HTTP coupling.

3 · Configuration dependencies (env vars)

Nothing is hard-coded. Services find their database and each other through environment variables, with sensible local defaults. Same code runs locally, in Docker, and on Render.

🧠 The golden rule: services are loosely coupled at runtime (HTTP + circuit breakers) but version-aligned at build time (one parent POM). Change one service's internals freely — as long as its HTTP contract stays the same, nobody else breaks.

Caching & Distributed Tracing

Redis caching in Post Service is built, deployed, and verified end-to-end — including two real bugs found and fixed during the verification pass. Distributed tracing is designed but not implemented yet — included here as the next roadmap step, presented honestly as a plan, not a finished feature.

Redis: read-through cache

Post Service is the only service with a cache today. Cache name posts, backed by Spring's RedisCacheManager + GenericJackson2JsonRedisSerializer (with default typing, so a cached List<PostDTO> and a cached PostDTO both deserialize back to the right Java type), TTL 60 seconds — configured in RedisCacheConfig.java.

💡 Analogy: the 60s TTL is a safety net, not the main defense — like a smoke detector you hope never actually has to go off, because the pub/sub invalidation below (the sprinkler system) reacts immediately, on every write.

Redis: pub/sub invalidation

On every write, Post Service also publishes a small JSON message to the post-cache-invalidate Redis channel. The publisher (PostCacheInvalidationPublisher.java) and the listener (PostCacheInvalidationListener.java) both live inside post-service — it's talking to itself, but through Redis, so eviction logic stays out of the write path itself.

Bugs found & fixed

Two real issues surfaced while verifying this feature end-to-end — worth showing, not hiding.

⚠️

TTL doc/code mismatch

Design docs and the README said 60s TTL. The actual code originally had Duration.ofMinutes(10) — a silent 10× longer staleness window than documented. Fixed to match the documented 60s.

fixed
⚠️

Cache key collision risk

getPostsByUserId originally used @Cacheable(value="posts", key="#userId") — a bare numeric key in the same cache region as getPostById's key="#id". If a userId and postId were ever the same number (e.g. both 1), a List<PostDTO> and a PostDTO could collide under one Redis key and risk a deserialization exception. Fixed by prefixing the key: key="'byUser:' + #userId", and extending pub/sub invalidation to cover it — the USER message type above didn't originally exist; it was added specifically to fix this.

fixed
Verified manually: curl requests + docker logs showing the eviction firing immediately + RedisInsight showing the actual keys and TTLs. No automated test suite for this yet — same known gap as the rest of the project.

Distributed Tracing future

Not implemented in code — design only. The next roadmap item after Redis, and (per the project's own README / delivery summary) the step before Prometheus + Grafana metrics.

[api-gateway, post-service, user-service, tag-service, comment-service, like-dislike-service]
        │  (OTLP gRPC, port 4317)
        ▼
  [OTel Collector] ──receives, batches, samples──▶ [Grafana Tempo] ◀── queried by ── [Grafana]
                                                          │
                                                  (object storage: S3 or local disk)

OTel Collector

Single ingestion point — every service pushes traces via OTLP instead of talking to Tempo directly. Config would have receivers (OTLP), processors (batch + tail_sampling — e.g. keep 100% of error traces, 100% of slow >500ms traces, 5% sample of everything else), and exporters (to Tempo via OTLP).

Grafana Tempo

Trace storage. Local disk backend to start (swappable to S3/GCS later without an architecture change). Retention e.g. 14 days (block_retention: 336h).

Grafana

Queries Tempo. Chosen over Jaeger specifically because it can later correlate traces with Prometheus metrics and logs in one UI — Prometheus/Grafana is already this project's own next-next roadmap item after tracing.

Per-service work needed

Add the Micrometer OTel bridge + OTLP exporter dependency, point it at the Collector's OTLP endpoint (not Tempo directly), and keep management.tracing.sampling.probability: 1.0 per-service — the Collector's tail_sampling makes the real sampling decision, not each service.

⚠️ Highest-risk part to verify once built: the trace must span both sides of the async post-created Kafka hop — a producer span in Post Service and a consumer span in User Service — under one trace ID. Don't assume Spring's auto-instrumentation "just works" across a Kafka hop under load; test it explicitly.

Alternatives considered

Zipkin

Simpler, but PoC-only — dropped because this project is moving straight into a production-facing setup, not staying a throwaway demo.

Jaeger

Good UI, but no built-in Prometheus/Grafana correlation — would mean a second, disconnected observability UI later.

Hosted vendor (Datadog / Honeycomb)

OTel Collector + a hosted backend — dropped for now: this is a local-first Docker Compose project, and the cost/infra overhead isn't justified yet.

Known gaps found during this audit

Found while verifying Redis end-to-end — not complaints about unrelated code, just things worth fixing before this goes further toward production.

🌐

Gateway CORS configured in two places

application.yml has a global CORS block allowing allowedOriginPatterns: "*", but GatewayConfig.java also defines a CorsWebFilter bean restricting to http://localhost:* and https://*.vercel.app. Open question: which one actually wins at runtime isn't clear without testing — flagging it rather than guessing.

🏷️

Tag traffic shows as "unknown"

The gateway's RequestTrackingFilter.resolveTargetService() only recognizes users/posts/comments/likedislike path prefixes. /api/tags/** requests fall through and show up as unknown in the live tracking dashboard.

🔗

Frontend tracking sidebar hardcodes localhost

RequestFlowDashboard.tsx hardcodes http://localhost:8080 for polling /api/tracking/requests, instead of the same VITE_API_URL env var the rest of the frontend uses. The live request-tracking sidebar silently doesn't work against a deployed (non-localhost) gateway.

🗄️

"Database per service" is table-level, not physical, by default

All services default to the same DB_NAME=main_db. The isolation story in the Overview tab is about each service owning its tables within one shared Postgres database by default — not physically separate databases — unless DB_NAME is overridden per deployment. Worth being precise about that distinction rather than letting the diagram imply full physical isolation.

The cool bit: live request tracking

📊

RequestFlowSidebar

Polls /api/tracking/requests every ~1.5s and shows the last requests that hit the gateway in real time — method, path, target service, duration, status. Great for seeing the architecture work.

Maps each request to the backend files involved, so the dashboard can teach you which Controller/Service/Repository handled it. A learning tool baked right into the UI.
